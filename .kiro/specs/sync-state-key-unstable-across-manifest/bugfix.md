# Bugfix Requirements Document

## Introduction

The durable interrupted-sync state (`.sync_state.json`) is keyed by the value
`resolve_drive_id(mount_point)` returns. That value is NOT STABLE for a single physical
drive across the card-manifest boundary: `resolve_drive_id` returns the drive's static
app-generated identity `id` ONLY when a valid card manifest also loads; when the card
manifest is absent or unparseable it returns `None`, and `run_sync_job` then falls back to
keying sync-state by the MOUNT PATH.

Because the drive's label (and therefore its mount path, e.g. `/Volumes/C2609P2610`)
changes by design every chart/plate cycle (`C<charts>P<plates>`), and because the card
manifest does not exist until the first successful sync writes it, the SAME physical drive
gets its interrupted-sync entries recorded under DIFFERENT keys at different times:

- A prior interrupted sync (card manifest present) records `begin_family("scanned")` under
  the static `id` (e.g. `234f0c5d-...`).
- A later successful sync that runs while the card manifest is absent/incomplete resolves
  `None` -> keys by the mount path, so its `complete_family("scanned")` clears the
  MOUNT-PATH entry and never touches the `id`-keyed entry.

The `id`-keyed interrupted entry therefore survives forever. On every subsequent insert,
once the card manifest exists, `resolve_drive_id` returns the real `id`,
`pending_families(id)` finds the orphaned entry, and the drive is forced through a full
legacy `--size-only --delete` verify+repair of that family — even though the drive is
actually current. This repeats on every insert and never self-clears.

Observed on 2026-10-31 with drive `C2609P2610` (id `234f0c5d-...`): a sync reported
"Drive Update Complete — Drive is current", yet `.sync_state.json` still held
`{"234f0c5d-...": {"families": ["scanned"], "started": "2026-10-24..."}}` (note the stale
`started` date — the entry was created by an older run and never cleared). The next insert
announced "Resuming interrupted sync: scanned" and launched a full legacy reconcile.

### Design principle (user-stated)

Sync state must be keyed off a drive identity that is STATIC after
adoption/preparation and INDEPENDENT of the drive label. The label is designed to
change with each chart/plate cycle, so it (and the mount path derived from it) must never
be a key. The drive's app-generated identity `id` in `EFIS_DRIVE_ID.json` is written once
at prepare/adopt and is exactly that static identifier; it is present even when the OS
`volume_uuid` is null (as it is on FAT32/exFAT drives) and even before any card manifest
exists. The sync-state key SHALL be that static `id`, decoupled from the card-manifest
"fully provisioned" check.

Note (for design): the OS/filesystem `volume_uuid` is NOT a suitable key — it is null on
the observed drive and is regenerated by a reformat (Start-clean), so it is neither
reliably present nor stable across a re-prepare. The app-generated `id` is the correct
stable key.

### Bug Condition

Let `syncKey(X)` be the value used to key `.sync_state.json` for a drive X on a given
operation. `identityId(X)` is the static `id` in X's `EFIS_DRIVE_ID.json`.

```pascal
FUNCTION isBugCondition(X)
  INPUT: X of type DriveOperation      // a managed drive mid/just-after a sync
  OUTPUT: boolean

  // The drive HAS a static identity id, yet the sync-state key resolves to
  // something other than that id (None -> mount-path fallback) because the
  // card manifest did not load at resolution time.
  RETURN identityId(X) <> NULL
         AND syncKey(X) <> identityId(X)
END FUNCTION
```

### Property Specification (Fix Checking)

```pascal
// Property: Fix Checking - sync-state key is always the static identity id
FOR ALL X WHERE isBugCondition(X) DO
  result <- F'(X)
  ASSERT syncKey(result) = identityId(X)
  // and therefore begin_family and complete_family within and across runs use
  // the same key, so a completed family is reliably cleared.
END FOR
```

Where **F** is the current key resolution (card-manifest-gated, mount-path fallback) and
**F'** is the fixed resolution (static `id` from the identity file, independent of the card
manifest).

### Preservation Goal (Preservation Checking)

```pascal
// Property: Preservation Checking - non-bug-condition behavior unchanged
FOR ALL X WHERE NOT isBugCondition(X) DO
  ASSERT F(X) = F'(X)
END FOR
```

Specifically: a drive with NO identity file at all still fails safe (no id -> no other
drive's state applied); a drive whose identity id already resolved stably (card manifest
present throughout) behaves identically; currency/recognition decisions that legitimately
depend on the card manifest are unchanged.

Concrete counterexample demonstrating the bug: drive id `234f0c5d-...`, first
manifest-building sync runs while no card manifest exists -> key falls back to mount path
`/Volumes/C2609P2610`; `complete_family` clears the mount-path entry; the pre-existing
`id`-keyed `scanned` entry survives and forces a needless full verify+repair on every
future insert.

## Bug Analysis

### Current Behavior (Defect)

1.1 WHEN `resolve_drive_id` finds a valid identity file with a static `id` BUT the card manifest does not load THEN it returns `None` instead of the `id`, discarding the stable key
1.2 WHEN `resolve_drive_id` returns `None` THEN `run_sync_job` falls back to keying the durable sync-state by the MOUNT PATH, which changes with the cycle-dependent drive label
1.3 WHEN one run records an interrupted family under the static `id` and a later run clears families under the mount-path fallback (or vice versa) THEN the two keys never reconcile and the interrupted-sync entry is never cleared
1.4 WHEN an orphaned interrupted-sync entry persists for a drive THEN every subsequent insert reports "Resuming interrupted sync" and runs a full legacy `--size-only --delete` verify+repair of that family even though the drive is current
1.5 WHEN sync-state keys are derived from transient mount paths (including retired mount-swap temp mounts like `/private/tmp/efis-datamanager/...`) THEN `.sync_state.json` accumulates orphaned entries that can never be matched again

### Expected Behavior (Correct)

2.1 WHEN a drive has a valid identity file with a static `id` THEN the sync-state key SHALL be that `id`, regardless of whether a card manifest is present
2.2 WHEN `begin_family` and `complete_family` run for the same physical drive — within a run and across runs, and across chart/plate cycle relabels — THEN they SHALL use the SAME static `id` key, so a completed family is reliably cleared
2.3 WHEN a drive has NO identity file at all THEN the resolver SHALL continue to fail safe (return no id) so no other drive's interrupted-sync state is ever applied
2.4 WHEN a sync completes cleanly for a family THEN the drive's interrupted-sync entry for that family SHALL be cleared such that a subsequent insert reports the drive current with NO verify+repair
2.5 WHEN the drive label / mount path changes due to a new cycle THEN the sync-state key SHALL be unaffected (label and mount path are never keys)

### Unchanged Behavior (Regression Prevention)

3.1 WHEN a drive legitimately has an interrupted (not-completed) family THEN the system SHALL CONTINUE TO detect it on re-insert and run verify+repair before declaring current
3.2 WHEN the card manifest is used to decide drive RECOGNITION / provisioning routing (identity-but-no-manifest -> route to Prepare/Adopt) THEN that decision SHALL remain available — this fix decouples the sync-state KEY from the card-manifest check, it does not remove the recognition check where it legitimately belongs
3.3 WHEN on-drive commit markers and payload are the source of truth for currency THEN that SHALL remain unchanged; the identity id keys sync-state only and never decides currency
3.4 WHEN a drive has an identity but the file is missing its `id` field THEN the resolver SHALL continue to fail safe (no id)
3.5 WHEN other drives' entries exist in `.sync_state.json` THEN operating on one drive SHALL NOT disturb another drive's entry (Property 6 preserved)

### Data Repair (orphaned entries)

4.1 WHEN this fix lands THEN existing `.sync_state.json` may still contain orphaned entries keyed by mount paths or retired mount-swap temp mounts (`/private/tmp/efis-datamanager/...`), and the stale `id`-keyed entry for the observed drive (`234f0c5d-...` scanned); these will not auto-clear merely by changing key resolution
4.2 The design SHALL decide whether to include a one-time cleanup that prunes sync-state entries whose key is not a currently-resolvable static `id` (e.g. mount-path-shaped keys, temp-mount keys), and how to reconcile the observed drive's orphaned `scanned` entry. (Open design decision.)

## Notes (non-authoritative — for design phase)

- Root cause location: `resolve_drive_id` (drive_updater.py ~742-808) returns `None` when
  `Manifest_Store.load_card(mount_point) is None` even though `identity.get("id")` is a
  valid static id (the `return None` inside the `if ... load_card ... is None` block,
  ~797). `run_sync_job` (~2048-2052) then does `drive_id = mount_point` as the fallback.
- All five callers of `resolve_drive_id` (drive_updater.py ~2048, ~2875; app.py ~425,
  ~743, ~1095) use it ONLY to key sync-state (`pending_families` / `begin_family` /
  `complete_family`). None need the card-manifest gate. Candidate fix: return the identity
  `id` whenever a valid identity file with an `id` exists, independent of the card
  manifest; keep the recognition/provisioning check (identity-but-no-card-manifest ->
  Prepare/Adopt) as a SEPARATE concern where it is actually consumed, not inside the
  sync-state key resolver. Consider a dedicated `resolve_sync_state_key(mount_point)` to
  make the single responsibility explicit.
- The app-generated `id` is present on the observed drive (`234f0c5d-...`) even with
  `volume_uuid: null`, confirming `id` (not OS VolumeUUID) is the right stable key.
- Validation: property tests (same physical drive, card-manifest present vs absent ->
  identical key; label/mount-path change -> identical key; begin+complete across the
  manifest boundary -> entry cleared) plus a regression fixture reproducing the
  `id`-vs-mount-path split that leaves `scanned` orphaned. Keep an exploration test that
  FAILS on current code (resolve returns None when card manifest absent) to confirm the
  bug before the fix.
- Backlog item: captured 2026-10-31 during chart-capable re-insert testing. Not yet
  scheduled. Related (separate) spec: sync-status-overwritten-by-chart-check.
